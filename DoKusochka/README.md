## DoKusochka Android App

### Обзор
**DoKusochka** — это мобильное приложение для управления заказами в контексте малого бизнеса (например, доставка еды или товаров). Оно включает:
- **Пользовательские функции**: просмотр товаров, управление корзиной, оформление заказа.
- **Админ-функции**: просмотр заказов и изменение их статусов (`in processing`, `being prepared`, `ready`, `in transit`).
- **Валидацию и бизнес-логику**, покрытую модульными тестами.

Проект реализован как **нативное Android-приложение** на **Kotlin** с использованием **Android SDK** и системы сборки **Gradle**.

---

### Структура проекта

Корень проекта:
- **`settings.gradle.kts`**: настройки Gradle (подключение модулей).
- **`build.gradle.kts`**: корневая конфигурация Gradle.
- **`gradle/`**: конфигурация Gradle Wrapper и version catalog.
- **`run_tests.bat` / `run_tests.ps1`**: вспомогательные скрипты для запуска тестов в Windows/PowerShell.

Основной модуль приложения: `app/`
- **`app/build.gradle.kts`**: конфигурация Android-модуля (версии SDK, зависимости, настройка тестов и т.д.).
- **`app/src/main/AndroidManifest.xml`**: манифест приложения (applicationId, активности, разрешения).
- **`app/src/main/java/com/example/dokusochka/`**: основная логика приложения на Kotlin.
  - Типичное содержимое (по структуре и тестам):
    - **UI-слой**: классы `Activity`/`Fragment` для экранов (список товаров, корзина, список заказов для админа).
    - **Доменные модели**: data-классы для товаров, элементов корзины, заказов, пользователей.
    - **Бизнес-логика**: менеджеры/сервисы для операций с корзиной, оформления заказа и изменения статусов.
    - **Утилиты**: вспомогательные функции для валидации, форматирования и т.п.
- **`app/src/main/res/`**: ресурсы.
  - **`layout/`**: XML-разметка экранов и элементов списков.
  - **`drawable/`**: иконки, фоны, векторные ресурсы.
  - **`values/`**: стили, цвета, строки, размеры.

Тесты:
- **`app/src/test/java/com/example/dokusochka/`**: unit-тесты (JVM, без устройства).
  - `BusinessLogicTest.kt` – проверка бизнес-правил (расчет цены, сценарии заказов и т.д.).
  - `CartManagerTest.kt` – тесты логики корзины (добавление/удаление, итоговые суммы, пограничные случаи).
  - `DataClassesTest.kt` – тесты моделей/data-классов (равенство, базовое поведение).
  - `EdgeCasesTest.kt` – проверка крайних случаев и исключительных ситуаций.
  - `ExampleUnitTest.kt` – пример теста по шаблону Android.
  - `ValidationTest.kt` – тесты логики валидации входных данных.
- **`app/src/androidTest/java/com/example/dokusochka/ExampleInstrumentedTest.kt`**: инструментальные тесты, выполняемые на устройстве/эмуляторе.

Сборка и отчеты (генерируемые файлы):
- **`app/build/`**: скомпилированные артефакты, объединённые манифесты, упакованные ресурсы и др.
- **`app/build/reports/tests/testDebugUnitTest/index.html`**: HTML-отчет о запуске unit-тестов.

### Высокоуровневая архитектура

Приложение реализовано в виде **слоистой архитектуры** внутри модуля `app`:

- **Презентационный слой (UI)**
  - Классы `Activity`/`Fragment` отображают экраны и обрабатывают действия пользователя.
  - Связывают элементы интерфейса (кнопки, списки, формы) из XML с кодом на Kotlin.
  - Делегируют сложную логику доменному/бизнес-слою.

- **Доменный / бизнес-слой**
  - Менеджеры и сервисы отвечают за:
    - Управление корзиной (добавление/удаление товаров, расчет сумм, обработка ограничений по количеству и т.д.).
    - Создание и обновление заказов.
    - Админские операции, такие как изменение статуса заказа.
  - Этот слой детально покрыт unit-тестами: `BusinessLogicTest.kt`, `CartManagerTest.kt`, `ValidationTest.kt`, `EdgeCasesTest.kt`.

- **Данные (data-слой)**
  - Для простого локального приложения данные могут храниться в памяти или в простых хранилищах (`SharedPreferences`, файлы, списки в памяти).
  - При необходимости этот слой можно заменить на полноценную БД (Room) или удалённый API.

Ответственность слоёв:
- **UI**: только взаимодействие с пользователем и отображение данных.
- **Домен**: бизнес-правила (например, допустимые статусы и переходы между ними).
- **Data**: хранение и получение сущностей (товары, заказы, содержимое корзины).

### Управление заказами и админ-функционал

В проекте реализован админский функционал **"View Orders"**:
- Администратор видит список заказов с основной информацией (клиент, позиции, сумма, текущий статус).
- Для каждого заказа администратор может изменить его статус.

Поддерживаемые статусы заказа:
- `in processing`
- `being prepared`
- `ready`
- `in transit`

Изменение статуса происходит на уровне бизнес-логики и проверяется тестами, чтобы гарантировать корректные сценарии и допустимые значения статусов.

### Схема БД (концептуально)

Текущая реализация ведёт себя как **локальное приложение с состоянием**, явного использования SQL или ORM по структуре проекта не видно. Однако концептуальная модель данных может быть описана так:

- **`Product`**
  - `id: String` – уникальный идентификатор.
  - `name: String`
  - `description: String`
  - `price: Double`
  - `imageUrl: String?` или ссылка на ресурс.

- **`CartItem`**
  - `product: Product`
  - `quantity: Int`

- **`Order`**
  - `id: String`
  - `items: List<CartItem>`
  - `totalPrice: Double`
  - `status: OrderStatus` – одно из значений: `IN_PROCESSING`, `BEING_PREPARED`, `READY`, `IN_TRANSIT`.
  - `createdAt: Long` / `Date`

- **`User`** (если используется)
  - `id: String`
  - `name: String`
  - `isAdmin: Boolean`

Если добавить реальную БД (например, Room), эти сущности можно отобразить в таблицы:

- `products` – товары.
- `orders` – заказы и их статусы.
- `order_items` – связи между заказами и товарами с количеством.

### API (концептуально)

Сейчас приложение выглядит как **самодостаточное** и не содержит backend-части в этом репозитории. Но внутренний API между слоями (интерфейсы и функции Kotlin) можно рассматривать как API приложения.

Примеры внутренних операций (Kotlin-функции/интерфейсы):

- **CartManager** (концептуально)
  - `fun addItem(product: Product, quantity: Int = 1): CartState`
  - `fun removeItem(productId: String): CartState`
  - `fun clearCart(): CartState`
  - `fun getTotal(): Double`

- **OrderManager / OrderService** (концептуально)
  - `fun createOrder(items: List<CartItem>): Order`
  - `fun getOrders(): List<Order>`
  - `fun updateOrderStatus(orderId: String, newStatus: OrderStatus): Order`

- **Утилиты валидации**
  - `fun validateProductName(name: String): Boolean`
  - `fun validateQuantity(quantity: Int): Boolean`

Если позже добавить backend, возможные REST-эндпоинты:
- `GET /api/products` – список товаров.
- `POST /api/cart` – обновление корзины.
- `POST /api/orders` – создание заказа.
- `GET /api/orders` – список заказов.
- `PATCH /api/orders/{id}/status` – изменение статуса заказа.

### Сборка и запуск

**Требования**:
- Android Studio (актуальная стабильная версия) или IntelliJ IDEA с Android-плагином.
- Android SDK версий, указанных в `app/build.gradle.kts`.

**Шаги**:
1. Откройте директорию проекта (`DoKusochka`) в Android Studio.
2. Дождитесь синхронизации Gradle и загрузки зависимостей.
3. Подключите устройство Android или запустите эмулятор.
4. В конфигурации **Run** выберите модуль приложения и нажмите **Run**.

### Запуск тестов

Из командной строки (PowerShell или cmd) в корне проекта:

- **Через Gradle**:
  - `gradlew.bat testDebugUnitTest`

- **Через вспомогательные скрипты**:
  - `run_tests.bat` – запуск unit-тестов с преднастроенной командой.
  - `run_tests.ps1` – PowerShell-скрипт для запуска тестов.

Запуск из Android Studio:
- Щёлкните правой кнопкой по пакету `test` в `app/src/test/java/com/example/dokusochka` и выберите **Run 'Tests in ...'**.

### Расширение проекта

Возможные направления развития:

- **Реальное хранение данных**:
  - Добавить Room для локального хранения товаров и заказов.
  - Отразить концептуальную схему на Room-entity и DAO.

- **Удалённый backend**:
  - Реализовать REST API и использовать Retrofit/OkHttp для загрузки товаров и синхронизации заказов.

- **Улучшение UI/UX**:
  - Постепенно переходить на Jetpack Compose (если нужно).
  - Добавить архитектурные паттерны управления состоянием (например, MVVM с ViewModel + LiveData/Flow).

- **Аутентификация и роли**:
  - Реализовать авторизацию пользователей.
  - Ограничить админские функции (управление заказами) только для админов.
